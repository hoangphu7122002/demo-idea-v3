# W3 · Demo moment (G3)

## 1. Before -> after
- Before: reader correction sits in a bottom-of-page comment / email / tweet; post body stays wrong; author must hunt stale posts by hand (E121, E122, E124, E129).
- After: reader highlights a sentence on the post, leaves a suggested edit anchored there; author accepts in one click -> post text changes, visible "Updated <date>: <reason>" note + diff appears inline, anchored comment stays attached after the edit (E035, E025, E130/E131).

## 2. Visible?
Yes for the suggest -> accept -> diff loop (screen change). Staleness signal is weaker: real staleness needs time/external changes; only visible with seeded "outdated" markers (E001, E122 want it; no evidence of a visible form readers accept).

## 3. <=2 min, <=5 clicks?
Suggest edit loop: highlight, comment, switch to author, accept = ~4 clicks, <1 min with seeded post. Staleness: needs days of real usage unless seeded/faked.

## 4. Generic AI wrapper risk?
Core loop is not AI. Risk rises if wow = "LLM flags outdated paragraphs" (E043 author already dumps posts into LLMs; E050 wants correctness check) — that is a generic wrapper demo. Anchor that survives edits (E035) is the non-CRUD technical piece but is invisible unless explicitly shown.

## Strongest wow evidence supports
Anchored reader suggestion -> one-click accept -> post rewrites live, comment re-anchors to edited/moved paragraph, public changelog note auto-added (E035, E124, E126, E122).

## Underwhelm check
Inline comments on web pages already exist and are demoed: Brevy (E069, PH), Hypothesis (E134/E135), Medium-style (E130). Giscus lacks it (E132) but the visual itself is familiar -> wow differential is the re-anchoring + accept-to-publish, which is subtle on screen.

## Mark: PARTIAL
Visible, fast before->after exists, but the visible part resembles existing inline-comment tools; differentiating part (re-anchoring, staleness) is subtle or needs time/seeded data.
